# 智能加载：运行时注入与 App 重建生命周期实战

<!-- 演进: 2026-10-01 | 来源: webhome/Python/智能加载-v7.0.py | 类型: 平台行为/生命周期/troubleshoot -->

适用于一切"管理型 py 源"（向 VodConfig 运行态反射注入/移除站点、触发 App 主动重载的 Spider）。核心教训：**App 重建站点表会销毁并重建所有 spider 实例**，围绕实例内存状态设计的功能都会被这条平台行为击穿。

## 平台事实（FongMi/WebHTV 壳实测）

1. 任何配置写盘/主动重载 → App 异步重建 VodConfig 站点表 → **对旧 spider 实例逐一调用 `destroy()`** → 新实例接管后续 UI 交互。
2. 重建时 `initSite` 找不到持久化 home key（站点刚被移除）→ **回退首站并 `config.save()` 覆盖持久化 home**（污染）。
3. `VodConfig.setHome(site)` 内含 `RefreshEvent.home()` + `config.save()`。
4. 运行态校验（`/manage/proxy/suggest/sites` 类端点）对"移除型"变更（perm→temp/移出/清除）会**提前通过**：旧运行态本就包含期望键集，校验在异步重建落地前结束。
5. 守护线程在实例销毁后仍存活（持有 self 引用），反射操作全局 VodConfig 与实例存活状态无关。

## 症状链（本轮三次"已修复仍失败"）

- perm→temp 转换后站点"出现又消失"，首页跳到首站。
- 根因①：同步注入赶在异步重建落地前 → 被重建冲掉。
- 根因②：补注时读 App 侧 `getHome()` → 读到已被污染的首站 key → home 永远恢复错。
- 根因③（最终根因）：`destroy()` 里反射移除临时站 + 清临时状态 + 置 `_destroyed` → 补注看门首轮 `_watch_aborted` 命中 → **静默退出**，站点无人补注。日志证据：重载成功日志同一秒打出、全程无看门日志（看门调用就在重载日志上一行）。

## 应对模式（已验证）

### 1. destroy() 禁忌

不在 `destroy()` 里做：反射移除运行态站点、清空功能状态集。临时站仅存运行态内存，App 进程退出即自然消失，无需主动清。`destroy()` 只应置标志位、取消本实例后台任务（如 `Event.set()`）。

### 2. 看门不随实例销毁中止

跨重建的后台看门线程，中止条件**不能含 `_destroyed`**（其工作时机恰在销毁发生期间）；保留代际检查（generation 不匹配则退出）即可。`_log` 不受 `_destroyed` 抑制、`_notify_app`(toast) 受抑制——排查以日志文件为准。

### 3. 两阶段看门（等待落地 → 补注 + 复查稳定）

```text
阶段一：轮询"临时站 key 是否已从运行态消失"（消失 = 重建落地的可靠信号；
        该 key 来自旧运行态残留，只有重建才会抹掉）。超时也继续，补注幂等。
阶段二：补注（首轮及每次被冲掉后的一轮带 restore_home）→ 复查，
        连续 N 次无缺失才判定稳定；被再次冲掉则继续补注。
```

### 4. home 自记，不读 App 侧

转换动作发生时把目标站 key 记入 `self._temp_home_key`；重建后补注用自记 key 恢复选中。绝不读 App 侧持久化 home（已被回退污染）。

### 5. perm→temp 转换 = 移出 + 临时加载两步

同步路径只做"移出"（从配置移除 + 写盘触发重建），**不做同步注入**；"临时加载"由看门在确认重建落地后执行——与文件浏览的临时加载走完全相同的纯内存注入路径（该路径稳定，因为不触发任何重建）。

### 6. 跨实例状态持久化 + PID 归属

实例内存状态不可靠 → `temp_identities`/`_temp_home_key` 随 `_save_settings` 落盘；加载时按 `android.os.Process.myPid()` 校验归属：同 PID（实例重建）恢复；异 PID（App 重启）丢弃——临时站已随运行态消失，不得复活。所有临时态变更点变更后立即 `_save_settings()`。

### 7. 纯内存产物要主动落盘（扫描快照同理）

"仅扫描"路径只填实例内存缓存、不写配置——若同时不保存扫描快照，退出 App 重进/刷新接口（新实例）后扫描结果全丢。**任何"刻意不写配置"的轻量路径，都要检查其产物是否有对应的落盘/恢复对**。启动恢复（`_restore_scan_snapshot`）早已存在，缺的只是仅扫描路径的 `_save_scan_snapshot()`；恢复快照的 token 校验（registry/包状态/扫描目录签名）不受"不写配置"影响，可安全复用。

## 取证方法

- 运行日志定生死：给看门各阶段打 INFO/WARN 日志（"已观察到重建/仍被冲掉/已稳定留存"），用户回传日志即可定位中止点。
- 录屏分析：无 ffmpeg 时 `pip install opencv-python-headless`，cv2 按 1 帧/秒抽帧 PNG 后逐帧读图，对齐 toast/骨架屏/首页跳转时间线。
- 桌面桩自测：假 `base.spider` 模块注入 + `Sp.__new__(Sp)` 绕过 `__init__` + 桩实例方法，可在无设备环境验证锁内逻辑/看门/持久化（注意 `_save_settings`/`_load_settings` 依赖属性多，桩要补全）。

## 排障口诀

重建必销毁实例 → destroy 别清理；看门跨销毁 → 莫查 _destroyed；移除型变更 → 校验不可信，等"消失"信号再补；home 被污染 → 自记不自取；状态跨实例 → 落盘 + PID；纯内存产物 → 落盘/恢复要成对。
